# Xoboro feature coverage

This is the release gate for replacing a Komga installation with Xoboro. It
tracks user-visible capabilities, not Komga endpoint or implementation parity.

Statuses:

- `READY`: usable through a supported interface and covered by automated tests.
- `PARTIAL`: the core works, but a material user workflow or hardening item is
  missing.
- `MISSING`: no complete production implementation exists.
- `FUTURE`: an Xoboro capability beyond the Komga replacement target.

"Covered by automated tests" means the tests exercise what a client actually
sends. A row can be `READY`, have code, have a large test suite, and still
describe something that does not work for most of a real library — that is what
happened to read progress, where every test was built from one shared request
helper that always supplied a `locator`, so a required-field defect broke every
comic while the suite stayed green. Test *existence* is therefore not evidence
on its own. Where a row's claim rests on cases that all share one fixture or one
request helper, say so in the row, and treat a fabricated request shape in an
acceptance test as a gap rather than as coverage.

| Natural ordering, dimensions, content detection, and hashes | READY | Add only formats required by new sources |
| Book, series, and read-list downloads | PARTIAL | All three are native and gated on the file-download permission: `GET /media-items/{mediaItemId}/file`, `GET /series/{seriesId}/file` and `GET /read-lists/{readListId}/file`. The two archive routes share `MediaArchivePlanner` and `MediaArchiveWriter` with the Komga-compatible surface rather than duplicating it, which puts the access filter in one place: an archive is planned per media item from the caller's `CatalogAccess`, so a member in an ungranted library or a series carrying an excluded sharing label is absent and its file is never opened — the hole the obvious "fetch the items and zip them" implementation leaves. Archives stream one member at a time, so they carry no `Content-Length`, `ETag` or `Accept-Ranges`; a client resumes through the single-item route. Remaining: a download affordance in the reader — no UI offers any of the three |
| Artwork upload, discovery, selection, generation, and caching | READY | Covers are generated **during analysis** for every media item and series, not only in the Komga compatibility sweep — running against a real library was what showed there was no artwork anywhere outside that sweep, while `Cover.svelte` documented the opposite. `BookCoverGenerationLifecycle` runs from `AnalyzeBookTaskHandler.afterAnalyze` and points the series' cover at the first item in reading order; it is built on `ArtworkLifecycle.replaceGenerated`, so uploaded artwork still wins and re-analysis replaces rather than accumulates. A comic or PDF uses its first page; an EPUB uses the cover its OPF manifest declares, recorded by analysis as the `EPUB_COVER` media-file kind (EPUB3 `properties="cover-image"`, or the EPUB2 `<meta name="cover">` fallback, and only when it points at an image). Nothing rasterizes spine markup — there is no browser engine here — so an EPUB with no declared cover is left without artwork, which is what the placeholder is for. A missing cover is a normal outcome and never a task failure: analysis has already succeeded and been persisted by the time this runs, so throwing would fail the task for something that worked. Collections and read lists derive a cover from their members: a 2×2 mosaic when four member covers are available, one member's cover otherwise, and the sweep re-derives a cover once the grouping's `updatedAtMillis` passes it, so a membership change is picked up without wiring the three mutation paths (ADR 0098). WebP is settled (ADR 0104): reading is supported through a pure-Java `ImageIO` reader, which fixed a real defect — the scanner offered to discover `cover.webp` while the decoder had no reader for it, so an ordinary WebP cover became a permanently failing artwork task. WebP **output** is declined, because every library that writes it binds to a native `libwebp` and the image is multi-architecture; a test asserts no writer is registered so a dependency bump cannot enable it silently |

Until recently `locator` was a required field, so **every progress write from the comic reader answered `400`** — comics have no spine and no `href`, so that reader sends a page alone, and only the EPUB reader, which sends both fields, ever worked. The lesson is about the shape of the coverage, not a missing test file: this row had a large suite, and every case in it was built from one shared `validRequest()` helper that always supplied a locator, so the suite exercised one request shape that no comic reader sends. The page-only shape is now pinned by a test written as raw JSON on the wire rather than through the DTO — constructing the DTO with a null would prove only that Kotlin accepts a null, not that a client omitting the field is accepted — and it asserts the stored locator is absent rather than `{}`, and that the staleness contract applies to page-only writes too. `locatorJson` is `String?` through the lifecycle, matching the `ReadProgress` invariant "null or non-blank" that the domain always modelled and only the request type refused to express. Kobo's `ProgressPercent` is that value and is now correct; the KOReader page mapping no longer inverts it but derives the stored page from `position` directly, so the display convention and durable read progress are independent. A round trip through the KOReader protocol pins the stored page at both ends, first position and last, and `V30__readium_total_progression.sql` restates already-analyzed positions |

Its acceptance rests on the same fabricated locator described in the Local-library end-to-end acceptance row. Remaining is a reader capability, not an administrator one — the previous entry here said "the administrator UI", which was wrong for every item in this row. **Marking read or unread has no native route**: the only native write is `PUT /media-items/{mediaItemId}/progress`, which records a position, so "read" can be reached by writing the last page but "unread" cannot be expressed at all. Explicit mark-read/mark-unread exists only on the Komga-compatible surface, per book and per series. The reader displays an unread state on the series screen and offers no control to change it |

## Xoboro extensions

These are valuable but do not count against Komga feature coverage.

| Capability | Status | Remaining work |
|---|---|---|
| WebDAV and other remote source adapters | PARTIAL | A read-only WebDAV source is implemented (`server/sources/webdav`) and registered alongside `local`: a library created with `provider: "webdav"` lists, analyzes and serves from a remote server.
