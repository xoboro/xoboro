## Authoritative objective correction

Do not pursue a percentage-based Komga parity target.

The objective is to build Xoboro as a good self-hosted media server by
reimplementing the useful user workflows that are appropriate for Xoboro.
`docs/feature-coverage.md` is a prioritization and release-risk ledger. It is
not an instruction to copy every Komga endpoint, DTO, database decision,
defect, or marginal feature.

Use these decision rules:

1. Implement the workflow a reader or administrator actually needs.
2. Design first-party APIs around Xoboro's domain and clients.
3. Preserve compatibility only for standards-based protocols and one-way
   migration where compatibility has independent value.
4. Improve unsafe, racy, slow, or accidental Komga behavior instead of
   reproducing it.
5. Prefer depth and production quality over inflated endpoint or line counts.

The repository `AGENTS.md` was corrected at the same time as this handoff.

## Product direction

Server work comes first. The public repository contains the Ktor server and
portable core code. Android and iOS applications will be developed later in a
separate private repository.

The long-term media hierarchy is:

```text
Library
└── MediaItem
    ├── Comic
    ├── Novel
    ├── Book
    ├── Video
    └── Audio
```

The current persisted catalog is book-oriented, but the native API exposes
`media-items`. Comic archives map to `COMIC`, EPUB to `NOVEL`, and PDF to
`BOOK`. Do not create another comics-only first-party API. Video and audio are
future extensions of the same hierarchy.

Remote sources such as WebDAV and offline native holdings are future Xoboro
features. They must use source/provider abstractions rather than being embedded
in local-filesystem assumptions.

## Repository architecture

```text
core/
  domain/             Platform-neutral entities and repository ports
  application/        Use cases and external-service ports
server/
  api/                Versioned first-party HTTP API
  app/                Ktor composition root and runtime
  media/              Analysis and content access
  metadata/           Metadata parsers/importers
  persistence/        SQLite migrations and jOOQ adapters
  security/           Password/session primitives
  sources/local/      Local source adapter
  tasks/              Durable leased background jobs
compatibility/
  komga-api/          Transitional adapters and standards protocols
  komga-differential/ Differential verification against reference Komga
```

First-party web/mobile code must use `server:api`, not Komga DTOs from
`compatibility:komga-api`.

  integrity.
- Durable prioritized task processing with leases, retries, and worker
  resizing.
